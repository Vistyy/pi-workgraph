# Autonomous run

## Purpose

Use this playbook when the user wants one bounded task driven to completion without routine human turns.
Autonomy means the coordinator owns reversible technical decisions and verification, not that it may cross product authority or irreversible boundaries.
Do not use this playbook to hide an unclear outcome or an unbounded program of work.

## Completion predicate

The run is complete only when the recorded checkable predicate passes against the exact composed revision, assurance is resolved, and no required node or evidence lane remains unsettled.
A plateau, timeout, or partial improvement is not completion.

## Step 1: `predicate`

Translate the requested result into a falsifiable predicate before the first state-changing unit.
Quantify the expected scope and name an escape condition for a genuine dead end.
Select the narrowest applicable change or investigation playbook as the inner procedure.
Record which decisions are reversible technical choices and which require human authority.
Present the normal implementation agreement before substantial product writes.
Do not weaken the predicate later merely to end the run.

## Step 2: `execute`

Run one smallest justified unit at a time through the implementation DAG.
Put blocking foundations and verification scaffolding before broad fan-out.
Use a pilot before repeated nodes when one bad brief could multiply failure.
Parallelize only disjoint scopes and keep one coordinator as graph owner.
After each uncertain process or Git result, reconcile durable session, worktree, commit, and repository state before retrying.
Address routine reversible failures with bounded replacement nodes instead of asking the user to manage agents.

## Step 3: `verify`

Verify every composed unit at its owned boundary before scheduling dependent work.
Run the complete predicate against the composed product at meaningful milestones and at the end.
Use independent product verification whenever commands do not observe the real behavior.
Key every verdict to the exact commit and invalidate affected evidence after corrections.
Treat INCONCLUSIVE as an unresolved state and improve the instrument or surface a real capability gap.
Do not use a worker's completion report as product proof.

## Step 4: `record`

Keep Workgraph state, playbook progress, node reports, model assignments, usage, commits, and evidence paths durable.
For a long or unattended run, maintain a compact append-only decision trail with one row per material unit or pivot.
Record rejected hypotheses and discarded changes when they explain why the final path was selected.
Use pointers rather than transcript dumps.
Write standing instructions into durable state before any interruption or resumed worker trajectory.
Do not create ceremonial logs for a short run that is already fully represented by state and commits.

## Step 5: `stop`

Stop only when the predicate passes or evidence establishes the recorded escape condition.
Run product verification, three-responsibility assurance, synthesis, and coordinator judgment before declaring success.
Route accepted local corrections without restarting settled work.
If an authority-changing decision is required, pause affected progress at a safe boundary and ask only that decision.
If a real dead end remains, report the evidence, attempted pivots, retained state, and smallest capability or decision needed.

## Failure and recovery

Do not spin on the same failed operation.
Classify failure as process, timeout, unavailable model, invalid report, verification failure, composition conflict, semantic escalation, or uncertain result before choosing a retry.
A resumed run begins with reconciliation rather than a blind repeat.
Keep unrelated safe work bounded by the accepted lifecycle; this version does not independently advance arbitrary graph branches during a human decision.

## Output

Report the predicate, units attempted, commits composed, changes discarded, exact product evidence, assurance decisions, final predicate result, and durable state path.
